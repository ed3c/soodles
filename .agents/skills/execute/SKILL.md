# Execute the admitted Issue

The installed provider entry revalidates the current provider Issue, external
envelope, canonical order, session and worktree before launching this Agent.
The stage prompt carries the exact binding, the supervisor's bounded `task`
and the complete validated structured Issue `contract`.
Use that contract. Keep source changes within its exact file boundary.
The implementation child needs no duplicate GitHub read.
If the contract is missing, stop the affected work. Return to the existing admission owner.
If the Issue body changes, obtain the supervisor's fresh envelope before further work.
Compare the supplied task's requested outcome with the contract while staying
within its file and effect boundary. Correct gaps within that boundary.
Return conflicting exclusions or missing admission to the supervisor.
Include the unmet outcome and its evidence. Do not reduce the requested outcome.
Do not change your own authority.
If the task requires a consumer, connect the data to that consumer.
If the task requires normal use, retain that work until normal use is observed.
A generated report alone does not meet either requirement.
The prompt is not permission to invent a new Issue, route, worktree or envelope.

For an admitted task that verifies Noodle CLI identity/skill resolution, stopped
initial-proposal recovery or a genuine order/session handoff, use
[verify-noodle](../verify-noodle/SKILL.md) and only its relevant feature recipe.
Its observations do not replace Soodles acceptance or delivery.

Use existing repository controls. Commit only the same causal correction.
Keep canonical acceptance, provider delivery and local reconciliation separate.
Do not merge, close Issues or change provider policy.
Do not select a new trusted verifier from the candidate.

Before reporting `completed`, reconcile the candidate and available evidence
with the supplied task's requested outcomes, not just its file list or passing
checks. Finish the admitted producers, consumers and integration.
In the outcome message, identify the evidence and work assigned to later owners.
An omitted writer requirement remains unfinished writer work. Publication may
follow this stage in the same owner call, without a supervisor review pause.

At the end of this stage, use the repository's `./stage-outcome OUTCOME MESSAGE`
entry from the admitted worktree. Choose exactly one outcome.
Use `completed` when this stage's admitted work, required checks and evidence are complete.
Use `blocked` when a required owner input or capability is missing.
Use `failed` when the task fails.
Give a nonblank message explaining the observed result, any observed gap and
work assigned to later owners. Stage completion does not claim those later outcomes.
The CLI derives the selected Noodle binary, session, order, stage and blocking
value from the current admission and owner readback. Do not reconstruct an event
payload. Do not search PATH for Noodle or ask for identifiers that the entry can derive.
If the CLI refuses, preserve its receipt. Obtain the named input from its owner.
Do not emit a substitute event or retry unchanged input.
After a recorded outcome, return naturally. This stage outcome is not Issue
resolution, publication permission or proof of the process's future exit.
The parent must not emit the worker's outcome.

When the stage prompt includes `instruction_context`, consume its exact selected
file contents at `source_head` for this task. The owner has checked the paths and SHA-256 values.
Do not select another recipe or replace the supplied bytes with current tips.
The supplied context does not prove that a model followed it.
Legacy prompts without this field retain their admitted task and contract.
They make no selected-instruction activation claim.
Return missing or inconsistent required context to the existing admission owner.
