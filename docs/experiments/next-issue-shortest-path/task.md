# Next-Issue shortest path — bounded atom

Question: after one exact landing is RESOLVED, can the system reach at most one
new GitHub Issue without asking the Agent to discover backlog, invent product
priority, deduplicate heuristically, assemble the Issue contract or choose
create transport?

Supervisor input is finite and semantic: one candidate packet. The executable
gate owns only mechanical truth:

1. validate terminal RESOLVED predecessor;
2. validate complete provider Issue frontier;
3. validate each candidate contract/repository;
4. reject duplicate causal fingerprint;
5. reject unmet dependencies;
6. reject overlapping open write boundaries;
7. auto-select only when exactly one candidate is eligible;
8. persist one exact create intent;
9. Cloud exposes the exact connector request; Local exposes one exact executable;
10. unknown create outcome produces readback only; never another create mutation;
11. one exact fingerprint/body provider match is terminal success.

Zero eligible candidates stop. Multiple eligible candidates require supervisor
selection. No hidden ordering rule is legal.

The atom stops at provider Issue identity. It does not schedule Noodle, create a
worktree, implement code, create a PR, merge, or close the newly created Issue.

CLI behavior is executable local evidence. The next-issue Skill is P-class and
cannot grant correctness authority. A P-class improvement claim requires fresh
matched model evidence; otherwise report only scoped alignment/nonregression.
