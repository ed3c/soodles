# NEXT-ISSUE.AUTHORITY.001

Owner: ed3c/soodles#124.

A completed landing lifecycle may propose another causal atom only through an
externally supplied finite candidate set. Semantic proposal remains supervisor
authority. The repository may mechanically qualify those candidates against a
complete fresh provider frontier, but it MUST NOT manufacture product priority
when more than one candidate remains legal.

The `next-issue prepare` entry accepts exactly five inputs: a terminal RESOLVED
landing receipt, finite semantic candidate packet, complete provider Issue
frontier, route descriptor, and new external output directory. Repository,
Issue title/body, causal fingerprint and create subject are not independent CLI
arguments.

For every candidate the gate validates the schema-1 semantic Issue contract,
registered repository, exact dependency closures, causal-fingerprint duplicate
state, and overlapping open write boundaries. Invalid or blocked candidates are
reported with exact reasons. Zero eligible candidates terminates without an
intent. Multiple eligible candidates require explicit supervisor selection.
Exactly one eligible candidate, or an explicitly selected eligible candidate,
may produce one persisted create intent.

The causal fingerprint binds repository, normalized trigger, semantic owner,
sorted write paths and exact dependencies. It is written into the Issue body as
a stable marker and is checked against the complete provider frontier before a
create intent is admitted. Title similarity is not duplicate authority.

Cloud route exposes the exact persisted provider-write request for the existing
connector. Local route exposes one executable continuation which consumes only
the persisted intent and supervisor-injected credential. No generic provider
mutation surface is introduced.

A provider create response that is unknown cannot be retried automatically.
The only legal continuation is fresh provider Issue readback. Reconciliation
adopts exactly one matching causal fingerprint and exact body; zero matches
remains readback-required and multiple matches refuse ambiguity.

Terminal success of this owner is one exact open GitHub Issue identity. It
creates no Noodle order, worktree, session, PR, merge or closure. Existing
Noodle backlog/completeness/schedule owners begin only after this provider
boundary.

N/P/L/R scope: candidate prose and this contract are N/P where applicable;
local qualification/refusal and intent integrity are L-class; actual GitHub
Issue creation/readback is R-class only for that provider identity.
